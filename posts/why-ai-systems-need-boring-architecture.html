Why AI systems need boring architecture

The flashy part of an AI product is the model. The part that keeps it alive is the plumbing around it.

Oct 18, 2026 · 6 min read

Every AI demo I've seen in the last year looked impressive for about five minutes. The trouble starts when real users arrive with real data and unpredictable expectations.

Start with the boring parts

Logging, retries, timeouts, and clear ownership of data matter far more than the choice of model. I now design the request path first and only then decide which model sits inside it.

The model is the easiest part to replace. The plumbing is what you will live with.

A simple rule I keep coming back to: if you can't replay a failed request, you can't debug it, and if you can't debug it, you can't trust it.

A small example

async function callModel(input, { retries = 3, timeoutMs = 15000 } = {}) {
  for (let attempt = 1; attempt <= retries; attempt++) {
    try {
      return await withTimeout(model.run(input), timeoutMs);
    } catch (err) {
      log.warn({ attempt, err });
      if (attempt === retries) throw err;
    }
  }
}

Nothing in that snippet is clever, and that is exactly the point.
